## 2026-11-23 (phase 2, slice 11): load test on this PC, desktop builds in CI

Tokens are minted directly (this tests the SFU, not our API). A first single-process version proved that one process cannot honestly drive 50 clients (it became the bottleneck: reconnects, 0.5 fps), so it was rebuilt with an orchestrator and worker processes.
- Measured on this PC (24 threads; the load generator and the SFU share the machine, which also runs other projects; SFU container limited to 2 CPU / 1 GB):
  - 30 participants (4 publishers, single process): all joined, none dropped, no reconnects, every subscriber held all 8 tracks; SFU about 25% of its CPU cap, ~200 MiB.
  - 50 participants (6 publishers, 5 worker processes, 60 s steady state): all 50 joined; 50 stayed connected, 0 disconnects, 0 reconnecting events; decoding watchers 8.5-10.0 fps per stream (floor judged: 8 fps); SFU cpu 120-140% of a 200% cap, memory ~340 MiB; whole-PC CPU 75-85% (this saturates the shared workstation: do not repeat casually).
  - NOT passed: one of the 44 subscribers held 11 of the 12 published tracks at the end of the steady state (49/50 had all). Cause not established (a late subscription or a generator-side artefact: the slowest native clients needed up to ~48 s to connect while the machine was saturated). An earlier 6-worker run showed the same saturation (SFU up to 160% of cap, whole PC up to 96%, ~7 fps) and a wrongly timed stability window, which was fixed in the script.
- Conclusions allowed by the evidence: 50 participants (6 publishing video) stay connected on this hardware without reconnects; the quality numbers (8-10 fps from synthetic 360p sources) were taken while the whole PC was close to saturation, so they are a lower bound for the SFU, not a capacity figure. A real capacity statement (plan: 100-200 participants per 16 vCPU node) needs a separate load-generator machine and a dedicated Linux media host: held (HELD.md).
- Join time: the native client takes 0.7 s (p50) but up to 48 s (p95) while saturated; browsers join in about 0.5 s in the e2e runs. The plan KPI "link to video <= 3 s" is therefore verified only for the browser path with few participants.
